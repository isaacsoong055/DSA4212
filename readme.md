# DSA4212: Bayesian optimisation vs CMA-ES

Group project for DSA4212. Authors and student numbers: [authors.md](authors.md).
Repository: https://github.com/isaacsoong055/DSA4212

We compare Bayesian optimisation (Gaussian-process BO with expected improvement, built on BoTorch) and CMA-ES
on black-box test functions, and ask which property of each method decides success. Each method carries an
implicit model of the landscape (a search distribution for CMA-ES, a GP surrogate for BO), and success depends on
whether that model's shape and scale match the problem. The project has two parts, one per author, with the same
folder layout:

| Part | Author | Question | Folder |
| --- | --- | --- | --- |
| Multimodality | Isaac Soong | At a fixed budget (N = 300), how do population size, restarts, step size and acquisition and surrogate choices change the probability of finding a narrow or distant global basin? | [`multimodality/`](multimodality/) |
| Geometry and parameterisation | Paul Ng | Does it matter more whether a method can tilt its search geometry to a rotated, ill-conditioned valley than which family it belongs to? Also units, bounds, invariances and noisy evaluations. | [`geometry/`](geometry/) |

The two parts use different budgets, metrics and BO implementations, so their results are never plotted on common
axes. Each part has its own pre-registered predictions, seeds and tests.

## Repository layout

```
readme.md              this file: overview, layout, how to reproduce (start here)
authors.md             names and student numbers
report/                the submitted report: source, bibliography, figures
multimodality/         Isaac's part
  readme.md            setup and commands for this part
  code/                optimisers, landscapes, configs, analysis, report helpers
  run_experiments.py   command-line entry point
  notebooks/main.ipynb all findings and figures for this part
  results/             saved numbers (summary/) and compressed raw BO runs (archive/)
  tests/  pilot/  docs/
geometry/              Paul's part
  readme.md            setup and commands for this part
  code/  results/  notebooks/  tests/  (same roles as above)
```

Why one folder per part and not one merged `code/` and `results/`: the two parts have different dependencies
(PyTorch/BoTorch against numpy/scipy only), different test suites and different result schemas, and each part's
scripts find their files relative to their own folder. Merging would have meant renaming and re-wiring both
code bases. The assignment suggests the names `code/` and `results/` but does not require them at the root.

## Environment

macOS / Linux, CPU only, Python 3.11+ (multimodality developed on Python 3.13, MacBook M2). Each part has its own
`requirements.txt` so versions do not clash; the simplest setup is one virtual environment per part.

```bash
# multimodality
cd multimodality
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m pytest -q

# geometry
cd ../geometry
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m unittest discover -s tests      # 11 checks, about a second
```

## Reproducing the main results

No data preparation is needed: every dataset is generated by the code from fixed seed lists.

**Multimodality.** The notebook `multimodality/notebooks/main.ipynb` (set `FAST = False` in the first cell)
loads the committed summaries in `multimodality/results/summary/` and redraws every figure and table in the report.
To regenerate the runs themselves, see `multimodality/readme.md`: `python run_experiments.py --full --exp exp0`
and so on (hours of compute; BO is about 100 s per run), then `--aggregate`. Raw BO runs are archived compressed in
`multimodality/results/archive/`. Smoke test (5 seeds, N = 100, about 5 minutes): `python run_experiments.py --fast`.

**Geometry.** The notebook `geometry/notebooks/main.ipynb` (Section 8, run from `geometry/notebooks/`) reloads
every number the geometry part reports from `geometry/results/`, and `python code/make_figures.py` (from `geometry/`)
redraws its figures. To regenerate the runs themselves, `./run_all.sh 8` from `geometry/` re-runs every experiment
in order (about 12-13 hours on 8 cores; each sweep checkpoints and resumes). See `geometry/readme.md` for the
per-experiment commands.

**Reproducibility notes.** Runs are seeded; random streams are derived from the seed. CMA-ES and random sampling
reproduce exactly. BO reproduces in distribution, not run for run, in both parts: floating-point differences
compound through the GP fitting loop, and in the geometry part even a single long run with BLAS pinned to one
thread can end differently in two processes (see `geometry/readme.md`, Repeatability). Comparisons are therefore paired on starting conditions.
